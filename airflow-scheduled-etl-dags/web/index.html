The tasks run in the order the graph asks for.

A four-task orders pipeline: extract, validate, aggregate and load. The order of the tasks comes from the dependency graph and not from the order they are written in, a task that fails is retried, and every run is written into the history of the warehouse.

What it does

The capabilities

Every panel below is served by the real API of this project — nothing here is a mock-up.

⇄

The order comes from the graph

A task only runs after the tasks it needs, even when the file is written in another order.

⟳

A failed task is tried again

A task that raises is retried twice, and the tasks that already ran are marked as rolled back.

▤

A warehouse of the results

The clean orders and the revenue of every day are written into SQLite.

⏱

Every run is in the history

The task, its state, its rows, its duration and the moment it finished are all kept.

◇

The same Airflow DAG

dags/orders_dag.py is a real Airflow DAG that calls the very same functions as the local runner.

⛁

No scheduler needed

The pipeline runs on one machine with a local runner and a file, so it is easy to read end to end.

Architecture

How it works

The DAG in dags/orders_dag.py declares the four tasks and their dependencies; the local runner in src/pipeline.py reads the same graph and calls the same functions, so the pipeline runs without Airflow installed. The raw orders are written to disk, the clean orders and the daily revenue become tables in SQLite, and every task lands in the task_runs history with its state, its rows and the seconds it took.
