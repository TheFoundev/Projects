The models run in the order their refs ask for.

A mini transformation layer: the SQL models of the project are ordered by the refs they call, the manifest says which model depends on which, and the raw tables and the models are materialised into SQLite.

What it does

The capabilities

Every panel below is served by the real API of this project — nothing here is a mock-up.

⇄

The order comes from the refs

The models are sorted by the refs they call, so a new model joins the run by itself.

⊘

A missing model is an error

A ref that names a model that is not there stops the run instead of making an empty table.

↻

A cycle is an error too

Two models that need each other are found and reported, not run in a loop.

▤

A manifest of the run

The manifest says which model depends on which, and how many rows every model wrote.

◫

The models are real SQL

The models of the models directory are plain SQL files, and they are run against the warehouse.

⛁

SQLite stands in for Postgres

The warehouse is a local file, so the project runs on one machine with no setup.

Architecture

How it works

The runner reads the SQL files of the models directory and finds the refs in them, and the order of the models comes from that graph: a model runs after the models it needs, a model that needs a model that is not there is an error and a cycle is an error too. The raw tables are loaded into SQLite, every model is rendered with its refs replaced by the tables that are already there, and the manifest of the run says what every model depends on.
